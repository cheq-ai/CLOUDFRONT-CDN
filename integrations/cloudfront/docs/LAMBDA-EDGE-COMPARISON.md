## Overview

AWS CloudFront Lambda@Edge allows you to run code at four different trigger points during request processing. The choice of where to run your RTI integration has significant implications for security, performance, and cost.

### Two Integration Patterns

| Pattern | Trigger Point | Cache Behavior | Blocking Location |
|---------|--------------|----------------|-------------------|
| **Viewer-Request** | At CloudFront edge, before cache | Checks every request | Blocks at edge |
| **Origin-Request** | After cache check, before origin | Only checks cache misses | Origin decides |

## CloudFront Request Flow

Understanding where Lambda@Edge functions execute is critical:

```
┌─────────────────────────────────────────────────────────────┐
│                    User Browser                             │
└─────────────────────────────────────────────────────────────┘

│  │  3. ORIGIN REQUEST  ← Approach 2 runs here         │     │

                           ↓
```

### Simple Restaurant Analogy

Think of CloudFront as a **fast food restaurant**:

- **Your Origin** = Kitchen (makes food fresh, slow)
- **CloudFront Cache** = Warming trays (pre-made food, instant)
- **Customer** = Website visitor

#### Viewer-Request (Security Guard at Entrance)
```
Customer enters → Security checks ID → Approved? → Check warming tray
```
**Every customer** gets checked, even for cached food.

#### Origin-Request (Security Guard at Kitchen Door)
```
Customer enters → Check warming tray first
   ↓
   Warming tray empty? → Security checks ID → Ask kitchen
   Warming tray has food? → Give immediately (no security check)
```
**Only customers needing fresh food** get checked.

## Approach 1: Viewer-Request

### Architecture

Lambda@Edge runs **immediately** when request arrives at CloudFront edge, **before** any cache lookup.

### Request Flow

```
User Request
    ↓
CloudFront Edge
    ↓
Lambda@Edge (Viewer-Request) ← RTI CHECK HAPPENS HERE
    ↓
╔════════════════════════════════════════════════════════╗
║ RTI Response                                           ║
╠════════════════════════════════════════════════════════╣
║ Bot Detected? → Return 403\404\Captcha\redirect        ║ ← User sees block page
║   ❌ Never checks cache                                ║
║   ❌ Never reaches origin                              ║
║                                                        ║
║ Legitimate? → Continue to cache                        ║ ← Normal flow
╚════════════════════════════════════════════════════════╝
```

### Characteristics

✅ **Advantages:**
- Maximum security - blocks at the edge
- Protects cache from poisoning
- Origin never sees malicious traffic
- Complete control over response
- Simpler origin setup (no header processing needed)
- All headers are sent 

❌ **Disadvantages:**
- RTI API called for **every request** (including cached content)
- Higher RTI API costs
- Higher Lambda execution costs
- Added latency on all requests (~70-200ms)
- Not all headers are available 

### Cache Behavior

```
Request 1 (User A):  RTI Check → Cache MISS → Origin → Cache → User
Request 2 (User A):  RTI Check → Cache HIT → User (no origin call)
Request 3 (User B):  RTI Check → Cache HIT → User (no origin call)
Request 4 (Bot):     RTI Check → BLOCKED (never checks cache)
```

**Important:** Even cached content triggers RTI checks.

## Approach 2: Origin-Request

### Architecture

Lambda@Edge runs **after cache check**, only when CloudFront needs to fetch content from origin (cache miss).

### Request Flow

```
User Request
    ↓
CloudFront Edge
    ↓
Cache Lookup
    ↓
╔════════════════════════════════════════╗
║ Cache Check                            ║
╠════════════════════════════════════════╣
║ Cache HIT? → Return immediately        ║ ← RTI NEVER RUNS
║   ✅ Fast response                     ║
║   ❌ No bot protection for cached hits ║
║                                        ║
║ Cache MISS? → Continue...              ║
╚════════════════════════════════════════╝
    ↓
Lambda@Edge (Origin-Request) ← RTI CHECK HAPPENS HERE
    ↓
╔════════════════════════════════════════╗
║ RTI Response → Lambda decides action   ║
╠════════════════════════════════════════╣
║ BLOCK  → Return 403/404 at edge        ║ ← Origin never sees this
║ CHALLENGE → Return CAPTCHA page        ║ ← Origin never sees this
║ REDIRECT → Return 302 at edge          ║ ← Origin never sees this
║                                        ║
║ ALLOW  → Inject x-cheq-rti-result hdr  ║
║   version=...;verdict=benign;...       ║
║   Forward request to origin            ║
╚════════════════════════════════════════╝
    ↓
Origin Server (only receives allowed traffic)
    ↓
Response → CloudFront → Cache → User
```

### Characteristics

✅ **Advantages:**
- Lower RTI API costs (only cache misses)
- Lower Lambda costs
- No added latency for cache hits
- Longer timeout (30 s vs 5 s hard limit) — more headroom for slow RTI responses
- Supports advanced challenge flows (Turnstile, reCAPTCHA) same as viewer-request

❌ **Disadvantages:**
- Cached content bypasses RTI checks entirely (bots with cache hits are never evaluated)
- Potential for cache poisoning (blocked content from a cache miss is not cached, but origin bugs could serve bad content)
- Only runs on cache misses — bots that hit cached pages pass through unchecked

### Cache Behavior

```
Request 1 (User A):  Cache MISS → RTI Check → ALLOW → Origin → Cache → User
Request 2 (User A):  Cache HIT → User (RTI NEVER RUNS)
Request 3 (User B):  Cache HIT → User (RTI NEVER RUNS)
Request 4 (Bot):     Cache HIT → User (BOT GETS CACHED CONTENT — RTI never ran)
Request 5 (Bot):     Cache MISS → RTI Check → BLOCK at edge (403) → origin never reached
```

**Critical:** Bots that hit cached content are never evaluated by RTI. Only bots that trigger a cache miss are checked and blocked at the edge.

## Detailed Comparison

### Performance

| Aspect | Viewer-Request | Origin-Request |
|--------|----------------|----------------|
| **Latency (Cache Hit)** | +70-200ms RTI check | 0ms (no RTI check) |
| **Latency (Cache Miss)** | +70-200ms RTI check | +70-200ms RTI check |
| **Cache Effectiveness** | Normal | Higher (no RTI overhead on hits) |
| **Origin Load** | Lower (blocked traffic stopped at edge) | Same — blocked traffic stopped at edge; only cache-miss allowed traffic reaches origin |

### Security

| Aspect | Viewer-Request | Origin-Request |
|--------|----------------|----------------|
| **Edge Protection** | ✅ Blocks at edge (every request) | ✅ Blocks at edge (cache misses only) |
| **Cache Protection** | ✅ Bots never reach cache | ⚠️ Bots with cache hits bypass RTI entirely |
| **Origin Protection** | ✅ Origin never sees blocked traffic | ✅ Origin never sees blocked traffic — only allowed cache-miss requests reach it |
| **Coverage** | 100% of requests | Cache misses only — cache hits are unchecked |
| **DDoS Mitigation** | Excellent | Poor for cached paths (cache hits bypass); Good for uncached paths |

### Cost

| Aspect | Viewer-Request | Origin-Request |
|--------|----------------|----------------|
| **RTI API Calls** | Every request | Cache misses only |
| **Lambda Executions** | Every request | Cache misses only |
| **Lambda Duration** | ~100-300ms | ~100-300ms |
| **Origin Bandwidth** | Lower | Higher |

**Example Cost (1M requests, 90% cache hit rate):**

```
Viewer-Request:
- RTI API: 1,000,000 calls × $0.001 = $1,000
- Lambda: 1,000,000 × $0.0000002 = $0.20
- Total: $1,000.20

Origin-Request:
- RTI API: 100,000 calls × $0.001 = $100
- Lambda: 100,000 × $0.0000002 = $0.02
- Total: $100.02
```

### Flexibility

| Feature | Viewer-Request | Origin-Request |
|---------|----------------|----------------|
| **Custom Block Pages** | ✅ Built-in Lambda | ✅ Built-in Lambda (same) |
| **Challenge Flows** | ✅ Full CAPTCHA integration | ✅ Full CAPTCHA integration (same) |
| **A/B Testing block pages** | ⚠️ Requires Lambda code change | ⚠️ Requires Lambda code change (same) |
| **Dynamic Blocking** | ⚠️ Requires Lambda config change | ⚠️ Requires Lambda config change (same) |
| **Origin analytics** | ✅ x-cheq-rti-result header on allowed requests | ✅ x-cheq-rti-result header on allowed requests (same) |

## Real-World Scenarios

### Scenario 1: E-Commerce Product Page

**Setup:**
- 100,000 daily visitors
- 95% cache hit rate
- Product pages cached for 1 hour

#### Viewer-Request Approach

```
Day 1 Traffic:
- Total requests: 100,000
- RTI checks: 100,000 (every request)
- Origin requests: 5,000 (cache misses)
- Bots blocked: 1,000 (at edge)

Cost:
- RTI API: 100,000 × $0.001 = $100/day
- Bots never reached origin ✅
```

#### Origin-Request Approach

```
Day 1 Traffic:
- Total requests: 100,000
- Cache hits: 95,000 (no RTI check — bots served from cache unchecked)
- RTI checks: 5,000 (cache misses only)
- Bots blocked at edge: 50 (Lambda returns 403, origin never reached)
- Origin requests: ~4,950 (only allowed cache-miss traffic)

Cost:
- RTI API: 5,000 × $0.001 = $5/day
- 950 bots accessed cached content (no RTI check) ❌
- Lambda blocked 50 bots at edge before they reached origin ✅
```

**Conclusion:** Viewer-Request provides better security (100% coverage); Origin-Request is more cost-effective. Both block at the edge — the difference is coverage, not where blocking happens.

### Scenario 2: API Endpoint (No Cache)

**Setup:**
- API endpoint: `/api/search`
- No caching (dynamic results)
- 50,000 daily requests

#### Viewer-Request Approach

```
Day 1 Traffic:
- Total requests: 50,000
- RTI checks: 50,000
- Origin requests: 50,000 (all are cache misses)
- Bots blocked: 500 (at edge)

Cost:
- RTI API: 50,000 × $0.001 = $50/day
- Origin protected from 500 bot requests ✅
```

#### Origin-Request Approach

```
Day 1 Traffic:
- Total requests: 50,000
- RTI checks: 50,000 (no cache, all are cache misses)
- Bots blocked at edge: 500 (Lambda returns 403, origin never reached)
- Origin requests: ~49,500 (only allowed traffic)

Cost:
- RTI API: 50,000 × $0.001 = $50/day
- Origin protected from all 500 bot requests ✅
```

**Conclusion:** For uncached endpoints, both approaches have identical RTI costs and identical origin protection. The only difference is the 5 s timeout constraint on viewer-request.

### Scenario 3: Credential Stuffing Attack

**Attack:** 100,000 login attempts to `/login` in 10 minutes

#### Viewer-Request Approach

```
Attack Traffic:
- Total attempts: 100,000
- RTI checks: 100,000
- Blocked at edge: 100,000 ✅
- Origin requests: 0 ✅
- Database queries: 0 ✅

Result:
- Login system never stressed
- No database impact
- Complete protection
```

#### Origin-Request Approach

```
Attack Traffic:
- Total attempts: 100,000
- First request: Cache MISS → Lambda blocks at edge (403) → origin never reached
- Next 99,999: Cache HIT → served from cache (RTI never runs, bot gets cached page)

UNLESS attacker varies parameters (cache-busting):
- /login?t=1 → Cache MISS → Lambda blocks at edge
- /login?t=2 → Cache MISS → Lambda blocks at edge
- /login?t=3 → Cache MISS → Lambda blocks at edge
- ... (100,000 unique URLs — all blocked at edge, origin never reached)

Result:
- Lambda blocks all cache-miss attempts at edge ✅
- Origin never receives bot requests ✅
- BUT: if /login has a cache TTL > 0, the attacker gets a cached
  response on subsequent hits without triggering RTI ❌
```

**Conclusion:** For uncached login endpoints, origin-request blocks as effectively as viewer-request. The real risk is if the login page is cached — then cache hits bypass RTI entirely.

## Cost Analysis

### Monthly Cost Comparison

Assumptions:
- 10 million monthly requests
- Cache hit rate: 80%
- RTI cost: $0.001 per call
- Lambda cost: $0.0000002 per execution (128MB, 200ms avg)

#### Viewer-Request Costs

```
RTI API:
  10,000,000 requests × $0.001 = $10,000

Lambda@Edge:
  10,000,000 executions × $0.0000002 = $2.00

CloudFront:
  10,000,000 requests × $0.0000075 = $75.00

Total: $10,077.00/month
```

#### Origin-Request Costs

```
RTI API (20% cache miss):
  2,000,000 requests × $0.001 = $2,000

Lambda@Edge (20% cache miss):
  2,000,000 executions × $0.0000002 = $0.40

CloudFront:
  10,000,000 requests × $0.0000075 = $75.00

Total: $2,075.40/month
```

**Savings:** Origin-Request saves ~$8,000/month (79% reduction)

### Cost Break-Even Analysis

The break-even point depends on cache hit rate:

| Cache Hit Rate | Viewer-Request Cost | Origin-Request Cost | Savings |
|----------------|---------------------|---------------------|---------|
| 50% | $10,077 | $5,075 | 50% |
| 70% | $10,077 | $3,075 | 70% |
| 90% | $10,077 | $1,075 | 89% |
| 95% | $10,077 | $575 | 94% |

**Key Insight:** Higher cache hit rates favor Origin-Request cost-wise, but sacrifice security.

## Security Implications

### Attack Surface

#### Viewer-Request (Smaller Attack Surface)

```
┌─────────────────────────────────────┐
│  Internet (Attackers)               │
└─────────────────────────────────────┘
              ↓
┌─────────────────────────────────────┐
│  CloudFront + Lambda (RTI Check) ←──┼── Attack stopped here
└─────────────────────────────────────┘
              ↓ (Only legitimate traffic)
┌─────────────────────────────────────┐
│  Cache Layer                        │
└─────────────────────────────────────┘
              ↓
┌─────────────────────────────────────┐
│  Origin Server (Protected)          │
└─────────────────────────────────────┘
```

#### Origin-Request (Larger Attack Surface)

```
┌─────────────────────────────────────┐
│  Internet (Attackers)               │
└─────────────────────────────────────┘
              ↓
┌─────────────────────────────────────┐
│  CloudFront Edge                    │
└─────────────────────────────────────┘
              ↓
┌─────────────────────────────────────┐
│  Cache Layer ←──────────────────────┼── Bots can access cache
└─────────────────────────────────────┘
              ↓ (Cache miss)
┌─────────────────────────────────────┐
│  Lambda (RTI Check)  ←──────────────┼── Blocks/challenges/redirects at edge
└─────────────────────────────────────┘
              ↓ (Allowed traffic only)
┌─────────────────────────────────────┐
│  Origin Server ←────────────────────┼── Never receives blocked traffic
└─────────────────────────────────────┘
```

### Threat Scenarios

| Threat Type | Viewer-Request Protection | Origin-Request Protection |
|-------------|---------------------------|---------------------------|
| **DDoS** | ✅ Excellent (every request checked) | ⚠️ Partial — cache hits bypass; cache misses blocked at edge |
| **Credential Stuffing** | ✅ Excellent (every attempt checked) | ✅ Good if login is uncached; ❌ Poor if login page is cached |
| **Scraping** | ✅ Good (all requests checked) | ⚠️ Poor for cached pages (bots served from cache); Good for uncached |
| **Account Takeover** | ✅ Excellent | ✅ Good for uncached auth endpoints; ⚠️ Poor if cached |
| **API Abuse** | ✅ Excellent | ✅ Excellent for uncached APIs (same as viewer-request) |
| **Cache Poisoning** | ✅ Prevented (blocked before cache) | ⚠️ Low risk — Lambda blocks at edge; but origin bugs could still cache bad content |

### Cache Poisoning Risk

Origin-Request has a lower but non-zero cache poisoning risk:

```
Attack Flow (origin-request):
1. Attacker sends malicious request with cache-busting parameter
2. Request has Cache MISS → RTI checks
3. RTI verdict = malicious → Lambda returns 403 at edge
4. Origin never reached → cache not poisoned ✅

Residual risk:
- If RTI verdict = benign (attacker evades detection):
  Lambda adds x-cheq-rti-result header and forwards to origin
  Origin processes request and response gets cached
  → same risk as any undetected attack, not specific to origin-request
```

Viewer-Request has no cache poisoning risk because every request — including the first cache-warming request — is checked before the cache is consulted. With origin-request, undetected malicious requests that reach the origin can poison the cache.

## When to Use Each Approach

### Use Viewer-Request When:

✅ **Security is top priority**
- Protecting sensitive endpoints (login, payment, admin)
- High-value targets (banking, healthcare, government)
- Regulatory compliance requirements (PCI-DSS, HIPAA)

✅ **Protection against DDoS is critical**
- High-traffic public websites
- API endpoints under attack
- Events/launches with expected traffic spikes

✅ **Cache hit rate is moderate (< 70%)**
- Dynamic content
- Personalized pages
- Real-time data

✅ **Budget allows for higher RTI costs**
- Security budget approved
- Cost of breach > cost of protection

### Use Origin-Request When:

✅ **Cost optimization is important**
- High cache hit rates (> 90%)
- Budget constraints
- Static content (images, CSS, JS)

✅ **Need more Lambda execution time**
- RTI API latency is higher than 4 s (exceeds viewer-request's 5 s hard limit)
- Timeout-sensitive environments

✅ **Need flexible response handling (same as viewer-request)**
- Challenge flows (Turnstile, reCAPTCHA)
- Custom block pages
- Business logic at origin

✅ **Turnstile/CAPTCHA integration required**
- Advanced challenge flows
- User verification workflows
- Multi-step authentication

✅ **Origin needs RTI context**
- Logging/analytics at origin
- Fraud scoring systems
- Custom business rules based on RTI data

✅ **Caching strategy favors Origin-Request**
- Long cache TTLs (hours/days)
- Mostly static content
- Low dynamic content ratio

## Hybrid Approach (Recommended)

For production systems, consider combining both approaches:

### Multi-Layer Defense

```
┌───────────────────────────────────────────────────────────┐
│              Viewer-Request Lambda                        │
│  ┌──────────────────────────────────────────────────────┐ │
│  │  Quick Checks (No RTI API Call)                      │ │
│  │  - IP blacklist/whitelist                            │ │
│  │  - Rate limiting                                     │ │
│  │  - Known bot signatures                              │ │
│  │  - Geographic blocking                               │ │
│  │                                                      │ │
│  │  Block immediately if matches ✓                     │ │
│  └──────────────────────────────────────────────────────┘ │
└───────────────────────────────────────────────────────────┘
                           ↓ (Suspicious traffic continues)
┌───────────────────────────────────────────────────────────┐
│                   Cache Layer                             │
└───────────────────────────────────────────────────────────┘
                           ↓ (Cache miss)
┌───────────────────────────────────────────────────────────┐
│              Origin-Request Lambda                        │
│  ┌─────────────────────────────────────────────────────┐  │
│  │  Full RTI Check                                     │  │
│  │  - Complete RTI API call                            │  │
│  │  - JA3 fingerprinting                               │  │
│  │  - Behavioral analysis                              │  │
│  │  - Add headers for origin                           │  │
│  └─────────────────────────────────────────────────────┘  │
└───────────────────────────────────────────────────────────┘
                           ↓
┌───────────────────────────────────────────────────────────┐
│                   Origin Server                           │
│  ┌─────────────────────────────────────────────────────┐  │
│  │  Process RTI Headers                                │  │
│  │  - Apply business logic                             │  │
│  │  - Custom responses                                 │  │
│  │  - Challenge flows                                  │  │
│  └─────────────────────────────────────────────────────┘  │
└───────────────────────────────────────────────────────────┘
```

### Benefits of Hybrid Approach

✅ **Cost Effective:** Most threats blocked by fast checks (no RTI API cost)
✅ **Comprehensive:** Complex threats caught by full RTI on cache misses
✅ **Low Latency:** Quick checks add minimal overhead (<5ms)
✅ **Flexible:** Origin can apply custom logic based on RTI data
✅ **Scalable:** Reduces load on RTI API

### Cost Comparison (Hybrid)

```
Viewer-Request (Quick Checks):
  10,000,000 requests × $0.0000002 = $2.00

Origin-Request (Full RTI, 10% cache miss after filtering):
  1,000,000 RTI calls × $0.001 = $1,000

Total: $1,002/month (90% savings vs pure Viewer-Request)
```

## Conclusion

### Quick Decision Matrix

| Your Scenario | Recommended Approach |
|---------------|---------------------|
| Banking/Payment systems | ✅ Viewer-Request |
| High-value accounts | ✅ Viewer-Request |
| Static content (images, CSS) | ✅ Origin-Request |
| API endpoints (no cache) | ✅ Viewer-Request |
| E-commerce product pages | ⚠️ Hybrid or Viewer-Request |
| Blog/News (high cache rate) | ✅ Origin-Request |
| Login/Signup forms | ✅ Viewer-Request |
| Admin panels | ✅ Viewer-Request |
| Public website | ⚠️ Hybrid |
| Need Turnstile/CAPTCHA | ✅ Either (both support challenge functions) |

### Summary

**Viewer-Request** = Maximum security, higher cost, best for sensitive endpoints

**Origin-Request** = Cost optimization for high-cache-hit workloads; blocks at edge same as viewer-request; 30 s timeout; unchecked cache hits are the key trade-off

**Hybrid** = Best of both worlds, recommended for production

### Next Steps

2. Identify critical vs non-critical endpoints
3. Calculate cost implications
4. Choose approach based on priorities
5. Implement monitoring and alerting
6. Test thoroughly before production deployment
